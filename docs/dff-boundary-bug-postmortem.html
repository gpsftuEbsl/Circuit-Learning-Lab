01 · 背景知識

為什麼路徑查詢一定要在 DFF 停下來？

數位電路可以分成兩種訊號網域：純粹用邏輯閘串接、沒有記憶的「組合邏輯」，以及被時脈鎖住、會保存狀態的「循序邏輯」。兩者的邊界，就是正反器。

組合邏輯

Combinational Logic

n3→ AND→ OR→ n9

訊號從輸入到輸出是「瞬間」傳遞的，路徑一定有限、一定會終止 — 這保證了圖是有向無環圖（DAG），簡單路徑數量有限且可枚舉。

循序邏輯

Sequential Logic

OR→ DFF (D→Q)→ AND

訊號要「等下一個時脈邊緣」才會從 D 傳到 Q。把 DFF 當作組合閘直接穿透，等於假裝時間不存在 — 狀態機的回授迴路會被誤判成一條「路徑」，圖因此出現環（cycle）。

04 · 為什麼會爆炸

DAG 上找路徑很快，但有環的圖不是

一旦 DFF 沒被擋下，回授迴路的節點就混進了 valid_nodes，DFS 要在「充滿環」的圖裡窮舉「不重複走訪同一節點」的簡單路徑 — 這是已知的 NP-Hard 問題，節點數一多就爆炸。

P

Polynomial Time（多項式時間）

節點數增加，運算量頂多是平方、立方成長，算得完、可預測。

例：DAG 裡找最短路徑 — 訊號只往一個方向流，路徑數量有限，掃一遍圖就結束了。

NP-Hard

沒有已知快速解法

沒人找到多項式時間的解法；規模一大，運算量呈指數 / 階乘成長（O(2ⁿ)、O(n!) 等級）。

這次踩到的問題：「列舉圖中所有簡單路徑」— 圖裡一旦有環，每個環上的節點都能選「繞 / 不繞 / 從哪切出去」，組合數瞬間爆炸。

✅ 修復版：只在組合邏輯 DAG 內搜尋—
❌ 漏洞版：混入回授環路後的簡單路徑組合數—
05 · 演算法選擇

同一張圖，為什麼反向用 BFS、正向用 DFS？

重點不是「方向」，是兩步驟要的答案根本不一樣 — 一個只要「集合」，一個要「一條條有順序的序列」。

反向 · 圈範圍

Reachability → 用 BFS（DFS 也行）

從 n9 往回找 valid_nodes，只是想知道「哪些節點跟這次搜尋有關」。答案是一個不管順序的集合，不用記住「怎麼走到那裡」。這種可達性問題，用 BFS 或 DFS 結果都一樣，換掉也沒差。

valid_nodes（集合，無序）
{ n9, g3, dff }
正向 · 列路徑

Enumeration → 一定要用 DFS

從 n3 走到 n9，要把每一條完整路徑序列印出來。DFS 天生就是「往一條路走到底，卡住就退回上一步（backtrack）換一條路試」— 這正是窮舉路徑的動作本身。BFS 佇列裡混著很多條路的節點，彼此不知道對方走過誰，沒辦法很自然地做「不能重複走訪」的檢查。

DFS trace（有順序，會 backtrack）
試: n3→g1→g2→dff→g3→n9 ✅ 找到一條
撤回，換路: n3→g1→(回授)→… ✗ 已走訪，撤回
　　→ 每條岔路都要走到底或撤回重來

也就是說：「不能重複經過同一節點」的檢查，正是簡單路徑（simple path）的定義，也正是 DFS 在有環圖裡會不斷嘗試、退回、換路，造成指數爆炸的根本原因。

修復方案

  • ✓
    反向 BFS 找 valid nodes 時　圈範圍往上游擴張前先檢查 gate['type']，若為 dff，只把它本身收進集合，但不再繼續往它的 D 腳上游展開。
  • ✓
    正向 DFS 找 consumer 時　列路徑同理，走到 dff 的 Q 腳輸出即停止延伸，不再往下一級邏輯閘展開。

  • ✓
